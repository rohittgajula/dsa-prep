## System design — 10 minutes, out loud

<!-- scenario -->
**A video platform transcodes every upload into 4 renditions. Uploads land on
one FIFO queue; a fixed pool of 200 GPU workers pulls from it. Normal load is
600 uploads/min and the pool drains 900/min, so upload-to-playable is about
4 minutes. A sports event pushes arrivals to 1,400/min for six hours. Failed
jobs are retried by pushing them back onto the same queue. By hour three the
backlog is 180,000 jobs and the newest upload is 7 hours from playable.**

1. What breaks first, and why
2. The design change
3. What that change costs, or when it stops working

<details>
<summary>What a good answer covers</summary>

Arrivals 1,400/min against a drain of 900/min is ρ > 1 — the queue grows by
500/min no matter how you tune it. Only more capacity or less work per job
fixes that; everything else is rearranging the wait. Two things make it worse
than the raw gap: one FIFO means a 40-minute 4K job blocks the 30-second clip
behind it, and retries re-enter the same queue, so a failing job eats capacity
twice and pushes the real drain below 900.
The change: split the queue by job class so short work is not stuck behind
long, and ship the 360p rendition first so the video is playable in about a
minute, generating the higher renditions lazily on first view. Autoscale on
queue *age*, not depth.
Costs: GPU capacity sized for peak sits idle the rest of the day; lazy
renditions mean the first viewer of a rare video gets low quality or waits;
fixed per-class worker splits are wrong the moment the upload mix shifts.
Push: you still have 180,000 jobs banked — do you drain oldest-first for
fairness or newest-first for freshness, and who do you tell?

</details>

## Concept — 5 minutes

<!-- concept -->
**The N+1 query problem** *(DBMS)*

You fetch a list of rows, then loop over the list and run one more query per
row. One query for the list, N for the items — N+1 round trips where one or
two would do.

An orders page shows 50 orders with the customer name. `SELECT ... FROM orders
LIMIT 50` is one query. Then each order does `SELECT name FROM customers WHERE
id = ?` — 50 more. Every one of those is a fast indexed lookup, but each still
costs a network round trip and a parse, say 0.4ms. That is 20ms of waiting
while the database is barely working, and it grows linearly with page size.

It hides well precisely because nothing is slow. The slow query log is empty
and every index is correct. The tell is a p99 that scales with how many rows
the page shows, and a service that got much worse when the database moved off
localhost.

ORMs produce it by default: `order.customer.name` is a lazy attribute that
fires a query the first time it is read, and nothing at the call site looks
like I/O.

Two fixes: **join** it into the original query, or **batch** — collect the 50
ids, run one `WHERE id IN (...)`, and stitch in memory.

<details>
<summary>Deeper — when it matters, and what it costs</summary>

If N is small and bounded — three queries on a detail page — leave it. It
matters when N tracks user-controlled page size, or when the loop is itself
inside a request that runs thousands of times a second.

Join vs batch is the real choice. A join duplicates the parent row for every
child: 50 orders each with 20 line items gives 1,000 rows with every order
column repeated 20 times. More bytes on the wire and more rows to deserialize.
Batching keeps the payload minimal, lets you cache per id, and is the only
option across two services — but it costs a second round trip, stitching code
in the application, and a query planner that handles a giant `IN` list badly,
so chunk it around 1,000 ids.

The opposite failure is eager-loading everything: now every request pays for
joins it never reads.

Detect it by counting queries per request in a test and asserting a bound.
The slow query log will not find it.

Push an interviewer will make: "You turned 51 queries into 2 and p99 barely
moved — why?" Because the round trips were the thing you fixed, not the work.
One `IN` over 50 scattered primary keys is still 50 random page reads; if
those pages are not in the buffer pool you pay the same disk time, just inside
a single query. Check the plan, not the query count.

</details>
